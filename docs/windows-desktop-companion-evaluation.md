# Windows 常驻桌宠评估

> 日期：2026-08-11
> 状态：评估文档，暂不实施
> 结论：**不默认进入当前 Web 工程**，留作后续 checkpoint

## 1. 背景与目标

当前 StudyMate 桌宠是网页内浮动层（`web/src/components/PetLayer.tsx`），受浏览器页面约束：
- 切换标签页 / 最小化窗口即不可见
- 无法在系统级常驻（开机自启、托盘、全局置顶）

本评估判断是否值得做一个 Windows 桌面常驻桌宠形态。

## 2. 目标场景

- 全局置顶桌宠：覆盖其他应用，随时可见
- 系统托盘：最小化到托盘，气泡提示
- 开机自启：随 Windows 启动
- 跨页面常驻：不随浏览器页面卸载
- 与现有 `/api` 交互：拉取学习状态、触发气泡

## 3. 方案对比

| 维度 | Tauri v2 | Electron | 原生 Win32 |
|---|---|---|---|
| 渲染与窗口能力 | WebView2 + 原生窗口 | Chromium + 原生窗口 | GDI/WinUI |
| 复用现有 `web/` 前端 | ✅ 直接打包 web/dist | ✅ 直接打包 web/dist | ❌ 需重写渲染 |
| 复用现有 Express `/api` | ✅ 壳内嵌 node/边缘侧 | ✅ 壳内嵌 node | ❌ 需另起服务 |
| 包体 | ~5-10MB（Rust） | ~80-150MB（Chromium） | ~1-3MB |
| 内存占用 | 低（WebView2 共享） | 高 | 极低 |
| 开发语言 | Rust + TS | JS/TS | C++/C# |
| 壳代码量 | 中（Rust 配置 + 权限） | 小（主进程 + preload） | 大（窗口/托盘/自启） |
| 托盘/自启/全局置顶 | 支持（插件） | 支持（成熟生态） | 支持（原生 API） |
| 自动更新 | 支持（tauri updater） | 支持（electron-updater） | 自建 |
| 维护成本 | 中 | 中 | 高 |

## 4. 技术成本估算

| 方案 | 粗略人日 | 关键风险 |
|---|---|---|
| Tauri v2 | 5-8 人日 | WebView2 版本差异、Rust 编译链首次配置 |
| Electron | 4-6 人日 | 包体大、内存高、安全审查 |
| 原生 Win32 | 10-15 人日 | 渲染重写、无复用、维护成本高 |

## 5. 与现有 Web 工程的关系（复用边界）

若未来实施，推荐 **Tauri v2 壳层方案**：
- 壳层只负责：窗口 + 托盘 + 自启 + 全局置顶，打包 `web/dist` 并代理 `/api` 到本地 Express 服务
- 桌宠业务逻辑（气泡、状态、活跃度分级）**仍在 React 内**，后端 `src/` 无改动
- Web 桌宠是 MVP 主干，桌面形态是壳层打包，不是新业务线

## 6. 结论

**不默认进入当前 Web 工程**。理由：
1. MVP 阶段优先验证核心学习闭环与网页内陪伴，桌面常驻是独立产品层
2. 依赖的数据模型（streak/relationship/活跃度）尚未完全稳定，过早做桌面壳会放大后续变更成本
3. 桌面常驻的价值（跨应用陪伴）属于长期陪伴的第二曲线，等网页内闭环跑通后再决策

本文档留作后续 checkpoint；触发条件：网页内桌宠交互数据验证通过 + 用户明确表达桌面常驻诉求。
